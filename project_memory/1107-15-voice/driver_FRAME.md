# driver FRAME (3b-8a): journal the session id before the vendor runs

Unfamiliar construct: an intent/ack rendezvous between two processes so a durable record exists before an irreversible effect. Prior art, named from knowledge and NOT re-fetched in this lane (UNVERIFIED as to current page text): the write-ahead log rule in SQLite's WAL design (https://www.sqlite.org/wal.html: the log record is durable before the change it describes is applied), the transactional-outbox pattern (https://microservices.io/patterns/data/transactional-outbox.html: record the intent in durable storage first, act second, a reaper cleans what the record names), and fsync-the-directory durability as in the existing `CleanupJournal.append`. The mapping here: `prepare` is the only place a session id is born (`seams.new_session()` inside the root helper), so "before mint" cannot mean before the id exists; the `intent` line is journaled before `prepare`, and the id is journaled before `render`/`start` (the first moment the vendor can run). `guest_dispatch.py` blocks at the `render` verb until the host writes `<tag>.journaled`, which the host does only after `start_session` has fsynced the id. A crash inside `prepare` itself (id born, reply lost) stays the documented ambiguous edge, covered by the `_levain_gw<n>` uid scan and the post-run slot-state check.
